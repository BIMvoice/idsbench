# idsbench

idsbench is a small tool for IDS (Information Delivery Specification) files from buildingSMART. It runs entirely in your browser: there is no server, and your files are not uploaded anywhere. It is one page around one document, the IDS file: open it to see whether it is valid, add a model to see whether the model meets it, and change the file right there when something has to change.

## What the page does

- **An IDS file arrives** (opened, dropped anywhere on the page, or started with New). It is checked at once against the official IDS 1.0 schema and the rules of the buildingSMART audit tool. The stamp says Valid or Not valid. Every finding is shown at the specification it concerns, with its sentence, its line, a short code and, on demand, the lines of the file around it. Under the stamp a list says what there is to fix: "Fix" opens the specification and puts the keyboard in the field concerned; where the engine already names the answer (a class written in other letters, a missing data type of a standard property, requirements on a prohibited specification, a missing IFC version) the fix is one press, offered only after the engine has confirmed it on the changed file, and it can be undone. A name that is one or two letters away from a real one is the engine's guess ("Did you mean"): it stays in the sentence and is not made one press. A problem that is in the text of the file and not in what it says (an attribute the standard does not know) is fixed by "Write this specification again in the standard form".
- **A model arrives** (optional, any time). It is read in a worker and kept there while it is the model on the page, so that a run after an edit only checks again. If the IDS file is valid the model is checked by itself: there is no Run button. The stamp becomes Pass, Fail or Incomplete, each specification shows its own state and counts, and its failing elements are listed grouped by reason. Elements that fail the same requirement are one group even when each has a value of its own in the reason (20,000 walls with 20,000 wrong names read as one reason; each wall's own value is in its row). "Download failing elements" gives the complete list as CSV for the people who model, with the requirement in words, what to fix and the storey or space of each element beside why it failed: the first column, "Row about", says "Element" on the row of a failing element and "Whole specification" on the row of a specification that failed as a whole (it needs a matching element and there is none), and "Not checked" on the row of a specification whose result is withheld (it did not fail, it has no result), so a filter on that column separates the three; a model whose only rows that do not pass are Not checked has nothing to hand over, and the button is not shown (the report records them) (UTF-8 with a byte order mark, so Excel reads it; a cell that a spreadsheet would run as a formula, one that starts with =, +, - or @, gets an apostrophe in front, which is not part of the name in the model); "Download report" gives the check and the run as one JSON file, which names the bytes it is about: the size and SHA-256 of the IDS text and of the model. If the IDS file is not valid, the model waits and is checked the moment the file is.
- **Compare with an earlier delivery** (optional, once a model is there). A coordinator who receives version 2 of a model chooses version 1 with "Compare with an earlier delivery" in the IFC box. The model on the page stays the model the verdict is about; the earlier delivery is run against the same IDS file in the same worker, after it, and kept there apart from it (the model is checked once more in a pass of its own to collect what the comparison needs, so its result on the page is never replaced, and removing the earlier delivery runs nothing), so neither pushes the other out and an edit only checks both again. One sentence says what changed ("building-v2.ifc against building-v1.ifc: 2 specifications now fail and 1 still fails."), a table names both models with their size and SHA-256, and each specification says Now passes, Now fails, Still fails (with the failing elements before and now), Still passes, or Not checked in one (nothing is compared then). Its elements are matched by GlobalId and listed by change, then by reason as in the failure list: Fixed (failed before; the specification applies to it now and it passes), No longer checked by this specification (failed before, still in the model, but the specification does not apply to it any more, so it is not known to pass), Element removed (failed before, not in the model any more), New failure (the specification applied to it before and it passed), Newly checked by this specification, failing (in the earlier model, which the specification did not apply to), New element, failing (not in the earlier model) and Still failing. To tell these apart each run also keeps the GlobalIds of every element a specification applies to. A failing element without a GlobalId, or with a GlobalId that another entity of either model also carries, cannot be matched; it is counted in a sentence of its own, never called fixed or new. "Download the comparison" gives it as CSV for the people who model (a row per specification and a row per changed element, both model names on every row; Excel-safe as the list of failing elements), and Download report then names the earlier model by name, size and SHA-256 beside the model (`earlierModel`) and holds the comparison. One model at a time is chosen on purpose: of two models dropped together nothing says which is the earlier one (the date of a file on disk is not the date of a delivery), so the page goes on taking the first and naming the other, as before, and the earlier delivery is always chosen by name. Without an earlier delivery the run, the page, the CSV and the report are what they were.
- **Editing in place.** Every specification reads as a sentence and has Edit, which opens its form in the row. IFC classes, predefined types, standard property sets, their properties, attributes and data types are chosen from pick-lists with type-ahead, built from the IFC tables the Check engine ships. A list holds what every IFC version ticked for the specification defines, and attribute names and property sets are those of the class the specification applies to, so that nothing a list offers is rejected by the engine; a plain name stands beside the technical one ("Wall (IfcWall)") and the technical form is what goes into the file. A custom name can still be typed. A new specification starts from one of five common shapes or from an empty form. It applies to the class and its subtypes in all three IFC versions ("Every wall, including wall standard case"; one control narrows it to the exact class), is optional (a model with no doors is not failed for it; the choice is in plain view), is named from what it says until a name is typed, and a shape never fills in a value that narrows the rule beyond its title. A name typed in a standard property set that the set does not define is said at the field, and names people look for by meaning ("number" for Reference) are found through a short hand-written table (`src/core/meanings.ts`, an aid, not the standard). The title of the IDS is suggested beside its field and never required: the official schema needs the `<title>` element but not a text in it, so a file without a title is written with an empty one and is valid. After a change the file is checked again and, with a model loaded, run again after a short pause.
- **No files at hand?** "Try an example" loads a small IDS file and model that ship inside the page.

**Large models.** The result keeps exact counts of everything and lists 200 failing elements per specification on the page; the complete list goes straight from the worker into the two downloads (as pieces the browser may hold on disk), so millions of failing elements are neither sent to the page nor kept in its memory, and the CSV and the report stay complete. The model is checked one range of entities at a time (400,000 of them, cut by count and not by how large their numbers are, so that a model whose numbers are far apart is not cut into thousands of empty ranges), so that the results of millions of elements are never all in memory at once. What a tab cannot hold is refused before it is parsed, in one sentence that says what to do: a file over 1 GB by its size, and a model with more entities than a tab holds. The entities are counted over the whole file, not estimated from a part of it, and weighed: an entity with a name or an identifier of its own (an element, a relationship, a property set) counts in full, every other (geometry, mostly) for a third, which is what each was measured to cost. The limit is 9.3 million of the first kind where the browser reports 8 GB of memory or more (the most it ever reports) or reports nothing at all (Firefox, Safari), and proportionally fewer where it reports less; the sentence gives the count and says which of these it is, and does not claim that the reader's computer was measured. The reader also has a limit of about 16 million distinct names and identifiers, and says so when it meets it. The worker tells the page that it is alive from inside its long steps (counting, parsing, checking); when it has said nothing for 30 seconds, or longer while a large model is being read (0.15 s more for every megabyte), the page offers "Stop and try again"; one that the browser ends without a word is noticed at once and said so. The IDS file is checked in a worker of the Check engine's own, which cannot say that it is alive; when that check has not answered in 30 seconds (3 s more for every megabyte of the file, about ten times what it was measured to take), the page says so and offers "Check again", and a run, which checks the file first, is refused with the same sentence and "Run again". A model that cannot be read any more (moved, deleted or saved again after it was chosen) is said as that. The report names the model by the SHA-256 of the bytes the worker parsed, taken when it parsed them, so the record is of what was checked even when the file on disk has changed since. Tab crashes that the page cannot see coming (the browser ending a tab for memory) cannot be caught by any page; the limits are set below the sizes that were measured to end one.

**What writing again leaves out.** A part of the file that is changed is written from what the editor holds. Before Download the page says, part by part, what that leaves out of the opened file, in words ("Writing specification 3 (\"Fire rating\") again will leave out: 2 comments, the attribute fixed on a list value."), and the JSON report carries the same list (`writingAgainLeavesOut`). It is worked out by comparing the XML of the part as the file has it with the XML written for the same content, node by node.

**Exact classes.** IDS matches the exact IFC class: a specification for IfcWall does not apply to an IfcWallStandardCase. Where a chosen class has subtypes in a ticked IFC version the specification says so in one line ("This applies to IfcWall only, not to IfcWallElementedCase or IfcWallStandardCase.") and offers, as an undoable action, adding the subtypes as a list. The list holds the subtypes of every ticked version, also one that only some of them have (IfcDoorStandardCase is a class of IFC4 alone, and an IFC4 model is where a list without it would pass over the doors; the Check engine accepts such a list). The one kind left out is a class that another ticked version puts under a different class (IfcZone is an IfcSystem in IFC4 and not in IFC2X3): the line names it and says why. A class that is abstract (IfcElement, IfcBuildingElement) can never be the class of an element: the line says that the specification applies to nothing as written, and the action puts the concrete subtypes in its place.

Two rules hold throughout. A result is never shown for another version of the document than the one on screen: each result is kept with the exact text and model it was made for, and is shown only while those are current. And the file you get is the file you made: a file that is opened and not changed is checked, run and downloaded as it is, byte for byte. Once something is changed, only the specification that was changed (or the info section) is written anew; everything else, comments, layout, line ends and byte order mark included, stays as the opened file has it, and a change that is typed back returns to the opened file. The record under the stamp says "with unsaved changes" while the document differs. Where a changed part held comments, the page says before Download that they are not kept.

idsbench accepts IDS 1.0 only. A file that declares any other version (0.9.7 included) is shown as Not valid with the engine's sentence, which names the version, and cannot be edited here.

Unsaved changes are kept in `sessionStorage` (this browser tab, gone when it closes), together with the text of the opened file they were made to, the page asks before you leave or open another file over them, and nothing is uploaded. After a reload the changes are restored and the page says so; a model is not kept and has to be chosen again. A stored draft that cannot be read is not used, and the page says that too.

An IDS file is read in the encoding it declares (UTF-8, UTF-16, ISO-8859-1 and the others a browser knows). Bytes that are not valid in that encoding are not replaced: the file is refused with the reason. A changed file is always saved as UTF-8.

The page reads IFC files in the STEP format (`.ifc`) for IFC2X3, IFC4 and IFC4X3. It does not read IFCX, ifcXML or zipped IFC files. A model it cannot use is refused with a sentence that says why: cut off, zipped, in an XML format or of another IFC version. A file that is not an IDS file at all is not opened, and what is on the page stays. An IDS file and a model are told apart by what they hold, so it does not matter which box a file is put in.

With a model loaded, each specification has one of four states:

| State | Meaning |
| --- | --- |
| Pass | The model meets the specification. For a prohibited specification: none of the elements it names is in the model. |
| Fail | At least one element does not meet it, a required specification matches nothing, or a prohibited specification matches something. |
| Nothing to check | An optional specification that matches nothing in the model. The standard counts this as a pass, and so does the headline, which says how many there are. |
| Not checked | No verdict: the specification names no elements to apply to, uses a text pattern that is not safe to run, or has its result withheld (see Known limits). The headline then never says that all passed. |

The record under the stamp counts "Records in the file" (every entity of the file), "Physical elements" and, when there are any, "Spaces". Physical elements are the entities of IfcElement and its subtypes (walls, doors, slabs, equipment, and the other feature elements such as IfcProjectionElement and IfcSurfaceFeature), except two kinds that are not counted: the feature subtractions (IfcFeatureElementSubtraction: IfcOpeningElement, IfcOpeningStandardCase in IFC4, IfcVoidingFeature in IFC4 and IFC4X3) and IfcVirtualElement. Spaces (IfcSpace) are counted apart, and the site, the building and the storey are neither. The count comes from the IFC tables of the model's version; where they cannot be had, it is not shown.

The IFC version a specification lists (`ifcVersion`) does not decide whether it is checked. The official test cases treat it as metadata ("Specification version is purely metadata and does not impact pass or fail result"), so every specification is checked, and a row whose listed versions do not include the model's version says so.

How many matching elements a specification allows has three values in IDS 1.0: at least one, any number, or none (`minOccurs` and `maxOccurs` 1 and unbounded, 0 and unbounded, 0 and 0; the developer guide says other values "are currently not allowed"). Any other number ("at most 2", "at least 4") is a problem the Check verdict reports, so the file is not run. The run engine also gives no result for such a specification when it is called by itself (its row is Not checked): the library would fail "at most 2" for three matches, and IfcTester looks only at whether each value is 0 and would pass it, so there is no answer to agree with.

An element the standard does not know, inside "Applies to" or "Must have" (a misspelt one, or one of another namespace), is a problem the Check verdict reports at its line and its specification: the official schema allows no element it does not name. The file is therefore not run; the library that runs the check would skip such an element without a word and check less than the file says.


## Known limits

**Ten classes the engine cannot tell from their parent (`@ifc-lite/ids` 3.2.0 on `@ifc-lite/parser` 9.2.0; their issue 7402, fixed in their pull request 7412, not in a release on npm yet).** The engine reads the class of an element from a table in which IfcBeamStandardCase, IfcColumnStandardCase, IfcDoorStandardCase, IfcMemberStandardCase, IfcOpeningStandardCase, IfcPlateStandardCase, IfcSlabStandardCase and IfcWindowStandardCase are folded onto their base class, and IfcDistributionControlElement and IfcDistributionFlowElement onto IfcDistributionElement, so a specification for the subtype alone applies to nothing, and a requirement or a pattern that names only the parent is met by the subtype; IDS matches the exact class. Only a model that holds an element of one of the ten is affected (none of the 307 official pairs does), and only a specification whose entity facet names the class or its parent in a way the fold changes (naming both, or neither, is not changed). The page takes the class from the line of the IFC file, which the parser keeps as written. A specification whose applicability is an entity facet with a class name, a list of names or a pattern (and no predefined type) is run with that class, and its counts and verdict are those IDS requires: they were compared element by element with IfcTester over 2,823 pairs of a specification and a model of IFC2X3, IFC4 and IFC4X3 (`scripts/fold-vs-ifctester`; 896 of the pairs have a pattern as the class name), identical in every one, while the engine on its own gave a different number of applicable elements or a different verdict for 1,513 of them. A pattern that could take long to work out (a group that repeats, a back-reference, over 200 characters) is not run, and neither is one written with a sign that the engine and IfcTester do not read alike, or that was not compared: a caret or a dollar (the two ends of the name for the engine, the characters themselves for XML Schema and IfcTester), a small letter (the engine ignores case, IfcTester compares with the class name in capitals), two patterns in one restriction (either for the engine and XML Schema, both for IfcTester), and what is not XML Schema at all (a lazy or possessive quantifier, `(?`, `\u`, `\x`). A review compared 42,148 more pairs written to break this (alternation, classes of characters, `\p{..}`, `\c`, `\i`, wildcards, quantifiers, a pattern beside every other kind of facet, the three cardinalities, typed IFC2X3 elements): before this rule 354 of the pairs run with the declared class differed from IfcTester and 350 could not be read by it; with it, none. In a model without the ten classes, and for a class the fold does not touch, such a pattern is run as the engine reads it, as before. Every other specification the fold changes (a pattern as the class name in a requirement or that could take long, a predefined type beside the class, an entity facet among the requirements, a partOf facet that names one of the classes, and in an IFC2X3 model a name the occurrence and type table answers for, such as IfcSensor, when the model holds IfcDistributionControlElement), and in such an IFC2X3 model any specification with an attribute facet for ControlElementId (the one attribute any of the ten has and its parent lacks, which the engine therefore does not find on the element), is not run: its row is Not checked, with one sentence that names the class, says that this version of the engine cannot tell it from its parent class, that the result is therefore withheld, and that a fixed engine version is on its way; the same sentence is in the CSV as a "Not checked" row (when a CSV is made, because something else failed; a specification that is not checked for another reason has such a row too, so the CSV holds as many as the headline counts) and in the JSON report (`withheld`, state `unchecked`). The correction and the notice are removed when the library is fixed: `tests/engine-version.test.ts` fails once `@ifc-lite/ids` 3.3.0 or later is installed. A failing element of one of the ten is still listed under the class the engine reports in a specification the fold does not change (a specification without an entity facet, for instance); its count and its verdict are not affected.

**Comparing two deliveries holds both models, and sends what it matches to the page.** The two models of a comparison are held in the tab at once, so they are counted against one budget, the one a single model is held to: before the earlier delivery is read it is counted beside the model already held, and a pair that does not fit is refused in one sentence (each may fit alone); the result of the model is not affected. The list of failing elements goes from the worker straight into the downloads; a comparison cannot, because it matches the elements of one model against the other, so each run made for it sends the page the GlobalIds of its model, of the elements each specification applies to and of its failing elements. These are capped at 500,000 for each model: a model with more is not compared at all (comparing part of them would call elements fixed or new that are not), and the page says so and what to do instead.

## Run it locally

You need Node.js 20.19 or newer.

```
npm install
npm run dev
```

Then open http://localhost:5173.

## Build

```
npm run build
```

The static site is written to `dist/`. Serve it with any static file server, for example `npm run preview` (http://localhost:4173). The built site makes no network requests of its own.

## How Check was measured

Check is the package in `packages/check` (see its README). It validates the IDS file against the official IDS 1.0 schema, then applies the rules of the buildingSMART IDS audit tool. Measured against the official tool on the IDS files in the two buildingSMART repositories: 425 of 425 IDS 1.0 files get the same valid or invalid verdict, and for the 80 the tool rejects the same set of error numbers. One more file declares IDS 0.9.7; the tool accepts it with a warning and idsbench refuses it by design. These files were used while building, so this is a regression guard, not an independent score.

- Audit tool: [buildingSMART/IDS-Audit-tool](https://github.com/buildingSMART/IDS-Audit-tool), MIT licence. Its rules and IFC tables are ported to TypeScript. idsbench is not endorsed by buildingSMART.
- Schema validator: [xmllint-wasm](https://github.com/noppa/xmllint-wasm) (libxml2 compiled to WebAssembly), MIT licence.

The Check engine is not part of the first load. It is fetched when the first IDS file arrives (about 456 KB over the wire, gzip, with its WebAssembly and the IFC 4 tables); the specifications are on screen before that, read by a small reader of the page's own, and the stamp says "Checking" until the engine answers.

## Privacy

Files are read and checked in your browser, in Web Workers. Unsaved changes to the IDS file are kept in `sessionStorage` only (cleared when the tab closes); nothing else is stored. Nothing is sent to a server, there is no analytics, and the page loads no fonts or scripts from other sites.

## Tests

```
npm test                                          # the MPL-2.0 notice on every source file, the app's unit tests, then the Check package's tests
npm run lint:headers                              # only the notice: lists the source files that lack it (node scripts/check-headers.mjs --write adds it)
npm run build && npm run check:browser -- <IDS clone> [a large .ifc]   # the six browser scripts in headless Chromium, network blocked (scripts/ASSERTIONS.md lists what they assert)
npm run truth -- <TestCases dir>                  # every pass-/fail- pair of the buildingSMART IDS test cases through Check and Run
npx vite-node scripts/roundtrip.ts <IDS clone> <ids.xsd with local imports> <out dir>   # read, write back and compare every IDS 1.0 file
node scripts/local-xsd.mjs <official ids.xsd> <dir with xml.xsd and XMLSchema.xsd> <out>   # the schema xmllint can read without the network
npx vite-node scripts/picklists.ts [--all-properties]   # everything the pick-lists offer, fed to the Check engine
npx vite-node scripts/fixes.ts <dir> [<dir> ...]         # every one-press fix over the IDS files the engine rejects
npx vite-node scripts/handover.ts <TestCases dir>        # CSV rows (element rows and whole-specification rows, counted apart), groups and report against the run's own counts
npx vite-node scripts/fold-vs-ifctester/run-app.ts <dir>   # the ten folded classes: the page against IfcTester, element by element (the steps are in scripts/fold-vs-ifctester/compare.py)
npx vite-node scripts/kept-model.ts <TestCases dir>      # a run served from the kept model against the run that read it
npx vite-node scripts/lost-check.ts <dir> [<dir> ...]    # what writing each specification again leaves out, and a proof that nothing else is
npx vite-node scripts/snapshot-results.ts <TestCases dir> <out.json>   # every result of the 307 pairs, for comparing two versions of the code (node scripts/compare-results.mjs a.json b.json)
node scripts/make-large-model.mjs <walls> <out.ifc> <pass|fail|filler> [<out.ids>]   # a model of any size, for measuring
node scripts/measure-browser.mjs <model.ifc> <spec.ids>   # time, longest freeze and peak memory of one model in the real page
```

`<IDS clone>` is a clone of https://github.com/buildingSMART/IDS; `<TestCases dir>` is its `Documentation/ImplementersDocumentation/TestCases`. Set `CHROMIUM_PATH` to use an installed headless Chromium. The inputs are used as they are; nothing is rewritten and no file is special-cased.

  Where the time goes (in Node, the same code, 4.3 million walls): reading and parsing the model a third, checking the elements against the specification half (it is the library's own work, per element), shaping the result and writing the downloads the rest; none of it is on the page's thread any more. The time of a first run did not change; what changed is what happens to the result: before, every failing element was copied to the page, grouped there and held there (a freeze of 1.8 s at 2.8 million, the end of the tab at 4.3 million); now the page receives counts, 200 rows per specification and the pieces of the two downloads. The largest model that works on this machine is the largest one the page lets in: 9.3 million entities (703 MB measured), 7.5 million of them all failing (520 MB measured); it is the memory of the parsed model (about 540 bytes an entity in the whole browser) that sets the limit, not the number of failing elements. After the first run of a model, a run after an edit does not read it again: with 700,000 entities of which 3 apply, "Checked in" is 1.00 s for the first run and 0.00 s for the run after an edit. The page stays responsive in all of these (longest freeze 2 to 36 ms).
